# 100 DAU Scalability Benchmark

**Status:** Not started  
**Target:** 100 daily active users

This document records the first scalability validation stage for Sendocs. It is a test plan until benchmark results are added; it does not claim that the current system supports 100 DAU.

## Objective

Establish a repeatable baseline for the current application and deployment. Validate that representative owner and client workflows remain correct and meet the performance objectives defined before the test.

## Workload

DAU alone does not define load. Before running the benchmark, specify:

- Requests per active user per day.
- Request creation and document upload frequency.
- Upload and download file-size distribution.
- Read/write mix and user-journey distribution.
- Average and peak requests per second.
- Expected concurrency, traffic ramp-up, and test duration.

Do not derive these values from DAU alone. The estimates in [design.md](../design.md) describe a 1K DAU hypothesis; they are not measured usage or a 100 DAU workload. Define and record a separate workload profile for this stage.

## Scenarios

Cover the main product workflows with a realistic mix:

1. Owner signs in and loads the dashboard.
2. Owner creates, lists, and views document requests.
3. Client opens a valid magic link and views required items.
4. Client uploads a document.
5. Owner views updated progress and downloads a document.
6. Owner deletes a document or request where included in the workload.

Use test data that avoids accidental duplicate uploads unless duplicate-upload handling is being tested.

## Test and acceptance

1. Run a smoke test to verify the environment and scenarios.
2. Run the defined 100 DAU load profile for the planned duration.
3. Check latency, throughput, errors, resource usage, database behaviour, background work, and file handling.
4. Verify data integrity, owner isolation, magic-link behaviour, and private file access.
5. Record bottlenecks and make no scaling changes unless measurements justify them.
6. Repeat the benchmark after any relevant change.

Set numeric latency, error-rate, and resource thresholds before the run. Use the existing performance objectives in [design.md](../design.md) as starting requirements and confirm they are appropriate for this workload. Do not choose passing thresholds after seeing the results.

A stage passes only when the agreed thresholds are met, business and security checks remain correct, and results are recorded. Otherwise, record it as blocked and address the measured cause before advancing to 1K DAU.
