# 1K DAU Scalability Validation

**Status:** Planned  
**Target:** 1,000 daily active owner accounts  
**Last updated:** 2026-11-14

## Objective

Validate that Sendocs can support 1,000 active owner accounts per day, plus the client portal activity generated by their document requests, while meeting the defined performance, correctness, and security requirements.

This is a benchmark plan, not a claim that the current system has demonstrated this capacity.

## Workload Model

The target counts active owner accounts. Client activity is additional workload and is included in the API request, upload, and download totals; clients do not need accounts.

The following are planning estimates from [design.md](../design.md), not measured production usage:

| Metric | Expected workload |
|---|---:|
| Daily active owners | 1,000 |
| API requests | ~10,000/day |
| Average API request rate | ~0.1 requests/second |
| Peak API request rate | ~1 request/second (10× average) |
| Requests created | ~200/day |
| File uploads | ~500/day |
| Average file size | ~5 MB |
| Upload volume | ~2.5 GB/day; ~75 GB/month |
| Maximum file size | 25 MB |

The request and upload estimates represent combined owner and client activity. Validate this interpretation against representative owner and client journeys before treating the estimates as a final workload profile.

Run the load progressively at 100, 250, 500, and 1,000 owner-DAU-equivalent workload levels. Scale request rates and background activity with each level; do not treat DAU as concurrent virtual users. Record the concurrency, ramp-up, and duration used for each run.

## System Under Test

Use the documented single-instance architecture as the baseline:

| Component | Baseline |
|---|---|
| Application | One application container serving the API and built React assets |
| Database | PostgreSQL |
| File storage | Private S3-compatible object storage |
| Background work | Account-email queue worker and PostgreSQL storage-cleanup scheduler |
| Deployment | Production-like environment; HTTPS and same-origin application/API |

Record the exact application commit, container/resource limits, database tier and configuration, storage provider, worker/scheduler configuration, and load-generator location with each benchmark run. Test only an environment you own or are authorized to test.

## Acceptance Criteria

Use the existing performance objectives in [design.md](../design.md) as the initial benchmark thresholds:

| Scenario | Target |
|---|---:|
| Request list with 1,000 requests | p95 under 200 ms |
| Client portal lookup | p95 under 150 ms |
| 5 MB file upload | under 3 seconds, excluding network latency |
| Error rate | under 1% |
| Peak API request rate | Sustain ~1 request/second |

The tested workflows must also preserve data integrity, owner isolation, magic-link security, and private file access. These are correctness and security requirements, not performance-only metrics.
