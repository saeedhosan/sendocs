# 1K DAU Scalability Validation

**Status:** Planned  
**Target:** 1,000 daily active owner accounts  
**Last updated:** 2026-11-14

## Objective

Validate whether the documented single-instance Sendocs architecture can support 1,000 distinct active owner accounts in a 24-hour period, including the additional client-portal traffic generated by their document requests.

This is a validation plan, not a claim that the system has demonstrated this capacity. A successful result applies only to the workload, dataset, environment, and configuration actually tested.

## Workload Model

### Actors and DAU definition

- **Owner DAU:** 1,000 distinct owner accounts that perform at least one authenticated product action during the 24-hour measurement window.
- **Clients:** unauthenticated recipients who use request-specific magic links. Their portal reads and uploads add workload but are not included in owner DAU.
- **Daily activity is not concurrency:** 1,000 DAU does not mean 1,000 simultaneous virtual users. Concurrency must emerge from the arrival pattern and time users spend between actions.

### Initial workload hypothesis

These are the current planning estimates from [design.md](../design.md). They are hypotheses, not production analytics or measured usage.

| Metric | Initial estimate | Interpretation |
|---|---:|---|
| Distinct active owners | 1,000/day | Unique owner accounts active in 24 hours |
| Combined API requests | ~10,000/day | Owner and client API calls |
| Average combined API rate | ~0.116 requests/second | 10,000 divided by 86,400 seconds |
| Peak combined API rate | ~1 request/second | Existing estimate; about 8.6× the daily average |
| Requests created | ~200/day | Owner request-creation actions |
| Successful uploads | ~500/day | Client file uploads |
| Average file size | ~5 MB | Planning estimate, not a size distribution |
| Upload data volume | ~2.5 GB/day | 500 × 5 MB |
| Maximum file size | 25 MB | Enforced product limit |

The daily totals are independent aggregates. The 500 uploads on a given day are not assumed to belong only to the 200 requests created that same day; clients may be completing requests created on earlier days. Likewise, 10,000 API calls are shared across owner and client journeys, not 10 calls made by every owner.

A useful cross-check is the minimum event budget implied by the agreed baseline assumption that each active owner opens the dashboard once per day, plus the documented upload behavior:

| Event | Daily count | Basis |
|---|---:|---|
| Owner session resolution | ~1,000 | One dashboard app boot per active owner |
| First request-list read | ~1,000 | One initial dashboard page per active owner |
| Request creation | ~200 | Existing planning estimate |
| Successful upload | ~500 | Existing planning estimate |
| Portal refetch after successful upload | ~500 | Client portal refetches after each successful upload |

This accounts for about 3,200 API calls/day before request-detail reads, additional list pages, client first opens, client returns/focus refetches, and other owner activity. The remaining ~6,800 calls are not yet assigned to journeys. During calibration, derive that remainder from observed or explicitly chosen journey frequencies (for example, owner detail revisits and client portal opens/returns), and document the resulting counts before running the target workload. Do not fill the gap with arbitrary endpoint traffic merely to reach 10,000 calls/day. Downloads also generate object-storage requests and bytes, which must be measured separately from API calls.

Do not use the aggregate request rate as a substitute for simulating the workflows below. Do not change the workload merely to make the acceptance criteria pass.

### Owner journey

Model owner activity as complete, stateful journeys rather than isolated endpoint calls:

1. Resolve an existing session when opening the dashboard.
2. Read the request list using cursor pagination; follow additional pages when the dataset requires them.
3. Open selected request details to inspect item states and available files.
4. Create a request with a valid title and between 1 and 10 required items; retain the returned link only for the simulated client journey.
5. Return to request details later to check derived progress.
6. Download selected uploaded files. The detail response mints signed URLs; file bytes are served directly by object storage.
7. Include less frequent lifecycle actions in separate scenarios: revoke a link, delete an uploaded document, delete a request, and delete an owner account where appropriate.

Do not assume every owner performs every action every day. The daily owner activity mix and the frequency of revisits, detail views, downloads, and destructive actions are not established by the current design estimates. Keep these as explicit workload parameters to calibrate rather than inventing percentages.

### Client journey

Model each client as an independent recipient using a reusable magic link:

1. Open the link and load the portal.
2. Upload one or more required files in any order, respecting the product's two-transfer concurrency limit; additional transfers wait in the visible queue.
3. Refetch the portal after successful uploads, and allow a later visit to the same link to observe previously completed items.
4. Include realistic incomplete journeys where the client leaves with items still waiting and returns later.

Use a distribution of request item counts from the supported range of 1–10 and a distribution of file sizes up to the 25 MB limit. The current 5 MB figure is only an average estimate; it does not define the distribution. Do not assume one download per upload or one client visit per request.

### Failure and lifecycle scenarios

Keep normal successful traffic separate from controlled failure scenarios so error injection does not distort the expected daily workload.

Exercise, and measure separately:

- Network or server upload failures followed by a client retry.
- Duplicate upload attempts, which must return 409 without creating a second document.
- Rejected file types and files over the size limit.
- Expired or revoked links, which must return the same 410 response.
- Rate limiting and retryable 429/500 responses.
- Owner deletion of a document, which returns the item to waiting and reduces derived progress.
- Request/document deletion and the asynchronous storage-deletion outbox.

Do not invent a normal-day failure percentage. Record the injected failure rate and scenario explicitly for each fault test.

### Arrival pattern and concurrency

The 10,000/day estimate implies about 0.116 combined API requests/second when averaged over 24 hours. The existing peak estimate is about 1 request/second. Preserve both as initial hypotheses, but do not assume a flat arrival rate.

The load profile must include:

- Requests arriving throughout the 24-hour period, with a realistic busy period and quieter periods.
- A ramp-up, sustained average-load period, peak burst, and cool-down.
- Owner and client journeys interleaved rather than running as separate endpoint-only tests.
- Think time between user actions and client upload duration.
- Upload bytes and object-storage downloads measured separately from API request throughput.

The exact time-of-day distribution and burst duration are not specified by current product data. State the chosen profile as a test assumption and include sensitivity runs for a sharper or longer peak. Derive virtual-user concurrency from the arrival rate and journey duration; do not set VUs equal to DAU.

### Progressive workload levels

Run the same behavioral model at these owner populations:

| Level | Distinct owner DAU | Combined API calls/day* | Requests created/day* | Successful uploads/day* |
|---|---:|---:|---:|---:|
| 1 | 100 | ~1,000 | ~20 | ~50 |
| 2 | 250 | ~2,500 | ~50 | ~125 |
| 3 | 500 | ~5,000 | ~100 | ~250 |
| 4 | 1,000 | ~10,000 | ~200 | ~500 |

*Linear scaling of the initial planning hypothesis, not observed usage. Keep the same journey definitions and distributions at each level. If evidence shows the ratios change with scale, record and explain the revised model rather than silently changing it.

### Test data

Prepare a repeatable dataset with:

- The target number of distinct active owner accounts.
- Requests spread across owners, including owners with multiple requests.
- Requests containing varied item counts from 1–10.
- A mix of waiting, partially uploaded, and complete requests.
- Documents with varied file sizes and valid allowed content types.
- Enough request history to exercise cursor pagination and the 1,000-request list acceptance scenario. For that specific latency scenario, seed 1,000 requests owned by one test owner; keep this separate from the distributed 1K-DAU population dataset.

Record dataset size and generation rules. Do not use one identical owner, request, item count, or file size for every virtual user. Use synthetic documents only; never use real client documents.

## System Under Test

Use the documented single-instance architecture as the baseline:

| Component | Baseline |
|---|---|
| Application | One application container serving the API and built React assets |
| Database | PostgreSQL |
| File storage | Private S3-compatible object storage |
| Background work | Account-email queue worker and PostgreSQL storage-cleanup scheduler |
| Deployment | Production-like environment; HTTPS and same-origin application/API |

Record the exact application commit, container/resource limits, database tier and configuration, storage provider, worker/scheduler configuration, dataset size, and load-generator location with each run. Test only an environment you own or are authorized to test.

## Acceptance Criteria

Use the existing performance objectives in [design.md](../design.md) as initial thresholds. These are separate from the workload model; passing them does not validate untested journeys or traffic patterns.

| Scenario | Initial target |
|---|---:|
| Request list with 1,000 requests | p95 under 200 ms |
| Client portal lookup | p95 under 150 ms |
| 5 MB file upload | under 3 seconds, excluding network latency |
| Error rate under the defined normal workload | under 1% |
| Peak combined API request rate | Sustain ~1 request/second |

Measure p50, p95, and p99 latency by endpoint and journey, throughput, response codes, and upload/download duration. Record network conditions so application/storage time can be distinguished from client-to-server transfer time.

Correctness and security are pass/fail requirements alongside performance:

- Owner data remains isolated; another owner's resource is not exposed.
- Magic-link unknown, expired, and revoked cases remain indistinguishable (410).
- One request item never accepts more than one document.
- Uploaded files remain private and downloads require valid short-lived signed URLs.
- Progress matches stored documents and can decrease after document deletion.
- Failed cleanup remains in the outbox and is retried without losing deletion intent.

## Benchmark Execution

1. **Prepare:** pin the application commit and environment; seed and verify the dataset; isolate the load generator from the system under test.
2. **Smoke:** execute each journey with a small number of actors and verify response correctness before increasing load.
3. **Calibrate:** verify that the generator produces the intended owner DAU-equivalent population, daily action counts, item/file distributions, arrival curve, and client revisit behavior.
4. **Progressive runs:** execute levels 100, 250, 500, and 1,000 using the same behavioral model. Record ramp-up, steady-state duration, peak duration, and cool-down. Shorter runs at 100/250/500 are useful for finding saturation points, but do not represent a full day of user activity.
5. **Target-day run:** run the 1K workload for a full 24-hour window to validate the daily activity target and observe daily background work. A compressed run may be used for faster iteration, but it must be labeled as a rate-equivalent test, not proof of a full 1K DAU day; compression changes concurrency and the timing of scheduled work.
6. **Soak and background work:** observe database connections, memory growth, queue delay, and cleanup backlog. Exercise the one-minute cleanup scheduler and verify eventual object deletion.
7. **Fault tests:** run the failure and lifecycle scenarios separately, then verify data integrity and security invariants.
8. **Repeat:** rerun material tests to distinguish stable bottlenecks from noise. Record environmental differences.

Use an open-source load-testing tool such as [k6](https://k6.io/). A shared GitHub Actions runner can validate scripts, but its shared resources are not a reliable measure of production capacity. Record where the application and load generator run.
